## 1. Цель

Сократить нагрузку на живую поддержку QIDRA за счёт бота первого уровня, который отвечает на типовые вопросы, собирает данные обращения, проверяет базовые статусы в системе и передаёт сложные или рискованные темы человеку.

Бот не должен принимать финансовые, юридические или инвестиционные решения. Он должен маршрутизировать, объяснять интерфейс и собирать данные.

## 2. Каналы

Каналы первого этапа:

- онлайн-чат на сайте;
- чат авторизованного участника;
- чат кабинета компании;
- админ-панель поддержки.

Каналы второго этапа:

- Telegram уведомления команде;
- email follow-up;
- WhatsApp только как ручной канал, если будет утверждён.

## 3. Какие данные бот может читать

Только после авторизации пользователя:

- имя пользователя;
- email;
- роль пользователя;
- статус профиля;
- статус KYC;
- список заявок участника;
- список проектов компании, если пользователь владелец/админ компании;
- статус инвестиционной заявки;
- статус пополнения;
- статус обращения в поддержку;
- публичные данные проекта;
- документы, доступные этому пользователю по правам.

Для гостя:

- имя, email, телефон, тема обращения;
- текст сообщения;
- вложения, если включены;
- browser token гостевого чата.

Запрещено боту:

- показывать чужие заявки;
- показывать чужие документы;
- показывать private keys, tokens, session data;
- показывать полный wallet secret;
- менять баланс;
- подтверждать платежи;
- проводить выплаты;
- менять статусы проектов;
- удалять документы;
- менять права доступа.

## 4. Стоп-темы с переключением на человека

Бот обязан сразу передавать человеку:

1. Потеря доступа к аккаунту.
2. Смена email.
3. Спор по платежу или пополнению.
4. Ошибка начисления дивидендов.
5. Запрос на вывод средств.
6. Запрос на удаление данных.
7. Жалоба на мошенничество.
8. Юридическая претензия.
9. Налоговый вопрос.
10. Инвестиционная рекомендация.
11. Обещание доходности.
12. Запрос договорной трактовки.
13. Ошибка в KYC/персональных данных.
14. Запрос приватных документов другого пользователя.
15. Любой вопрос, где пользователь пишет: "срочно", "юрист", "суд", "полиция", "верните деньги".

## 5. Основное дерево сценариев

### 5.1 Вход и регистрация

1. Пользователь не может войти.
2. Бот уточняет email и тип аккаунта: участник или компания.
3. Бот проверяет, существует ли аккаунт.
4. Если аккаунта нет - предлагает регистрацию.
5. Если аккаунт есть - предлагает восстановление пароля.
6. Если ссылка не приходит - передаёт человеку.
7. Если email менялся или есть спор владения - сразу человек.

### 5.2 Профиль участника

1. Пользователь не может отправить анкету.
2. Бот проверяет заполненность обязательных полей.
3. Бот показывает список незаполненных/ошибочных полей.
4. Если ошибка связана с валидацией корректного текста - передаёт человеку и помечает как баг формы.
5. Если профиль отправлен - сообщает статус проверки.

### 5.3 Компания и листинг

1. Компания не может создать листинг.
2. Бот проверяет статус профиля компании.
3. Бот проверяет наличие обязательных документов.
4. Бот проверяет статус черновика.
5. Бот объясняет, где продолжить заполнение.
6. Если кнопка не отправляет или ошибка неясна - человек.

### 5.4 Инвестиционная заявка

1. Пользователь спрашивает статус заявки.
2. Бот показывает статус: draft, submitted, approved, rejected, funded, cancelled.
3. Если нужна причина отказа - показывает публичную причину, если она сохранена.
4. Если причина отсутствует - человек.

### 5.5 Пополнение и кошелёк

1. Пользователь отправил USDT.
2. Бот просит tx hash.
3. Бот проверяет, есть ли tx hash в системе.
4. Если транзакция найдена - показывает статус.
5. Если не найдена - объясняет допустимую сеть и передаёт человеку.
6. Если сеть неверная - только человек.

### 5.6 Дивиденды и выплаты

1. Пользователь спрашивает, когда выплаты.
2. Бот показывает только утверждённые периоды и публичное объяснение графика.
3. Бот не обещает выплату и не рассчитывает вручную.
4. Если пользователь спорит с суммой - человек.

### 5.7 Документы

1. Пользователь не видит документы проекта.
2. Бот проверяет права доступа.
3. Если документ публичный - даёт ссылку.
4. Если документ доступен только участникам - объясняет условие доступа.
5. Если документ должен быть доступен, но не открывается - человек.

## 6. Тональность

Тон бота:

- коротко;
- без обещаний доходности;
- без юридических гарантий;
- без давления;
- с понятной следующей кнопкой.

Запрещённые фразы:

- "гарантированная доходность";
- "точно получите";
- "без риска";
- "мы вернём деньги по первому требованию";
- "это точно халяльно" без ссылки на утверждённый документ;
- "проблем нет", если есть открытое обращение.

## 7. Данные, которые бот должен собирать перед передачей человеку

Для участника:

- email;
- user id;
- тема;
- проект;
- номер заявки;
- tx hash, если платёж;
- скрин/файл, если есть;
- краткое описание проблемы;
- последние 3 действия пользователя.

Для компании:

- email;
- organization id;
- project/submission id;
- статус листинга;
- какие файлы загружены;
- текст ошибки;
- browser/device.

## 8. Очереди поддержки

Рекомендуемые очереди:

- `TECH_SUPPORT` - баги, вход, форма, загрузка файлов.
- `SALES` - вопросы по проектам и размещению.
- `PAYMENTS` - пополнения, вывод, дивиденды.
- `COMPLIANCE` - KYC, документы, юридические вопросы.
- `ADMIN_ESCALATION` - права, владельцы компаний, спорные изменения.

Если в Prisma пока есть только часть очередей, новые значения добавлять только через отдельную миграцию.

## 9. MVP бота

Первый релиз:

1. FAQ-ответы по 20-30 типовым вопросам.
2. Проверка статуса профиля.
3. Проверка статуса заявки.
4. Проверка статуса проекта компании.
5. Сбор контекста перед передачей человеку.
6. Стоп-темы.
7. Логирование всех ответов бота в thread.

Второй релиз:

1. Проверка tx hash.
2. Проверка документов.
3. Автоматическое создание internal task для поддержки.
4. Оценка SLA.
5. Автоматическое определение языка.

## 10. Метрики эффективности

Измерять:

- доля обращений, закрытых ботом;
- доля обращений, переданных человеку;
- среднее время до первого ответа;
- среднее время до решения;
- топ-10 причин обращений;
- количество повторных обращений по той же проблеме;
- количество багов, найденных через поддержку.

## 11. Риски

Главные риски:

- бот даст финансовое обещание;
- бот покажет чужие данные;
- бот выполнит действие вместо человека;
- бот скроет критический инцидент;
- бот не передаст срочный случай человеку.

Меры защиты:

- read-only режим для MVP;
- жёсткие стоп-темы;
- все ответы бота сохраняются;
- оператор видит summary и исходный диалог;
- финансовые/юридические темы только через человека.
